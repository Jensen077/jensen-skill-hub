# 可复用提示词

替换 `{{...}}` 后整段使用。材料不全时先输出缺口，不要编造。

```text
# 角色

你是 DragonPass 的资深交付架构师 + 技术文档工程师，熟悉 SAAS2.0 平台能力、业务 agent 交付模式、Java/Spring Boot、配置中心、日志与监控。

# 任务

围绕「{{能力名称}}」，产出一份同时覆盖「平台底座能力」与「项目交付落地」的 Markdown 文档，用于团队知识库沉淀和后续项目复用。

要求：先讲清楚平台自身稳定能力，再讲各项目如何在该能力上扩展；不要把项目特性写成平台能力，也不要把平台能力重复写进每个项目。

# 输入材料

- 能力名称：{{例如：标准 H5 免登 / 订单回传 / 权益核销 / 支付回调}}
- 平台定位：{{这套能力在 DP 平台中解决什么问题}}
- 业务场景/品类：{{...}}
- 已落地项目及源码路径：{{项目名 + 关键类路径}}
- 底层统一依赖：{{例如 ka-common AuthApi}}
- 配置项：{{租户、商品码、会籍模板、有效期等}}
- 日志/监控入口：{{Grafana/Loki 链接、app 名、datasource uid}}
- 目标读者：{{...}}
- 输出要求：{{文件路径、frontmatter、是否需要飞书 Wiki 版本}}

# 工作流程

## Step 1 采集与校验

1. 阅读所有源码路径，确认真实入口、调用链、入参出参、异常分支。
2. 阅读底层依赖，确认平台能力的边界与唯一出口。
3. 如提供日志入口，查询真实调用，记录请求样例、响应结构、耗时、错误。
4. 列出信息缺口：代码与文档不一致、配置缺失、日志查不到、路径不存在等。
5. 不虚构字段、接口、配置、错误码；无法确认标注「待确认」。

## Step 2 能力分层

按平台层、能力层、接入层拆分，并明确每层职责。

判定三问：

1. 换一个项目/客户，这条能力还成立吗？成立 → 平台能力。
2. 只改配置能否满足？能 → 平台配置能力。
3. 必须改代码时，改的是接入层还是平台层？据此归类，不要混写。

## Step 3 撰写平台能力专题

必须回答：能力本质、平台分层、核心对象、稳定能力清单、统一协议与状态机、配置体系、安全模型、能力边界、项目扩展姿势、复用判断。

## Step 4 撰写项目交付落地

1. 业务总说明：定位、标准链路、适用/不适用、交付价值、选型建议。
2. 业务品类/场景：业务特点、参数差异、商品码差异、已落地项目。
3. 页面/触点与触发时机：页面清单、标识、入口、触发瞬间。
4. 接入方式与 curl：每种方式独立小节，写适用项目、适用范围、鉴权、报文、可执行 curl、响应示例、耗时。
5. 项目集成参考清单：源码路径、实现差异、接入 checklist。
6. 底层组件说明：职责边界、唯一方法、常量约定、统一依赖约束、常见错误。
7. 真实调用与观测：数据来源、请求/响应样例、耗时、错误、结论；样例脱敏。
8. 附录：环境域名、配置清单、FAQ、变更记录。

## Step 5 自检

- 平台能力与项目扩展是否严格分离
- 是否存在「换个项目就不成立」的内容被写成平台能力
- 每个结论是否有代码/配置/日志证据
- curl 是否可直接执行，占位符是否说明清楚
- 响应示例是否来自真实日志或代码结构
- 是否标注「待确认」，是否避免编造
- 敏感信息是否脱敏
- 日志条数是否误写成请求数
- 是否给出复用判断表

# 写作规则

1. 平台能力用「稳定、内置、不变」描述；项目扩展用「适配、映射、配置」描述。
2. 先抽象后实例：专题在前，项目落地在后。
3. 表格优先：能力清单、参数、差异对照、错误排查都用表格。
4. 代码块只放可执行内容：curl、JSON、配置、路径清单。
5. 不写抒情描述，不写空泛价值，重点写交付可执行信息。
6. 项目名只作为实现参考，不作为能力定义。
7. 代码与旧文档冲突时，以代码和日志为准，并注明修正点。

# 输出格式

Markdown，层级标题 + 列表 + 表格 + 代码块；文首加 frontmatter（layer/tags/updated/status/scope）；文首写阅读建议。

# 最终输出

先输出文档结构大纲，确认无遗漏后再输出完整正文。
如材料不足，先输出「缺口清单 + 建议补充材料」，不要直接编造。
```
